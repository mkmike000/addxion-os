Wiederverwendbare Bauweise. Welche Locale gilt: [i18n de und en](../decisions/i18n-de-en.md).

# Ein Satz

Strings aus dem Code, Locale aus einem Signal, Formate aus `Intl` / React Aria. Nicht drei Wahrheiten für dasselbe Wort.

# Catalog

Ein Key, zwei Dateien (`de`, `en`). Key ist Englisch und nennt das Ding (`nav.products`, `auth.login`). ICU nur wo Zahl oder Name die Grammatik kippt.

Quelle der sichtbaren DE-Stimme bleibt Redaktion, nicht der Key. EN ist zweite Fassung, nicht `de` durch ein Modell jagen.

Fehlender Key bricht CI oder fällt hart auf den Key-Namen, nicht still auf Deutsch in einer EN-Ansicht.

# Signal

Reihenfolge, oben gewinnt:

1. URL-Präfix auf öffentlichen Seiten (`/en/…`)
2. Gespeicherte Preference (`locale`)
3. Cookie nach Umschalter
4. `Accept-Language`
5. Default `de`

Umschalter immer sichtbar, wo Sprache wechselt. Automatik ist Schätzung.

# Formate

Datum, Zahl, Relativzeit, Sortierung: `Intl` und `@internationalized/date` über React Aria `I18nProvider`. Kein `toLocaleDateString()` ohne Locale. Kein hartes `"de"` in `localeCompare`.

Währung ist Markt, nicht Sprache. Formatter bekommt `currency` extra.

# HTML

`lang` am Dokument. `og:locale` plus `og:locale:alternate`. Öffentliche Schwesterseiten: `hreflang` und Canonical auf die eigene Locale, nicht alle auf `de`.

# Schnitt

Zuerst Chrome: Nav, Login, Fehler, leere Zustände, Toasts. Dann Home und Produkt-Hub. Dann Rest. Recht zuletzt und von Hand.

LLM-Prompts (Inspiration, Chat-System) folgen der wirksamen Locale, sonst antwortet das Modell Deutsch in der EN-UI.
